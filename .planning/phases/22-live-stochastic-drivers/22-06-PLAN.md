<!-- The three gaps, read out of the shipped code. -->

SC-4 — the generator sends NOTHING at N = 0. `StochasticOrderGen.Rpc.run_order_gen` does
  `mapM (create_orders owner manager) (chunk max_batch built)` and `chunk _ [] = []`. A
  zero-arrival Poisson tick therefore produces zero chunks -> zero eth_calls -> zero transactions.
  The 64-byte empty return — named in v4.0's exit record as "the single clause in the return
  contract most likely to break StochasticOrderGen" — is never exercised by the generator path.
  EXERCISE BOTH READINGS: (a) assert the generator's N = 0 path completes cleanly with zero chunks;
  (b) call `create_orders owner manager []` DIRECTLY.
  A TRANSACTION RECEIPT CARRIES NO RETURNDATA. The "exactly 64 bytes" fact is observable ONLY
  through the preview `eth_call`, never through the mined tx. Say that in the check's haddock;
  do not write a check that pretends otherwise.

SC-3 — the rejected tuple must be WIDTH-valid and DOMAIN-invalid, because
  `pack_vol_order_input`'s field-width validation rejects out-of-range values CLIENT-SIDE before
  anything is sent. `offchain/rig/capture-batch-return.sh` already identified and used the
  discriminator LIVE in Phase 21: **skew = 65535**, because `spread_tick_assimetry_is_complete`
  admits only [1, 65534] while u16 admits 65535.
  Its comment calls this "the ONLY input a client can pass that the contract rejects". That
  exclusivity is NOT verified (research flags it LOW confidence) — USE the discriminator, do not
  depend on its uniqueness, and do not repeat the "only" claim.
  `strike = 0`, `width = 0` and `targetVega = 0` are also domain-invalid and width-valid; confirm
  against `pack_vol_order_input`'s guards before relying on any of them, never assume.

SC-2 — already shipped end to end (`create_order` -> `report_receipt` -> `decode_order_created`,
  and `create_orders`'s `verify_mined_order` does the receipt-block-pinned readback). What is
  missing is the ASSERTION over recorded evidence, not the code path.

WHAT `create_orders` ALREADY ENFORCES (do not re-implement, just record its outputs):
  - preview decode + length match against the submitted batch
  - `receiptStatus == 1` gate, else fail with the tx hash
  - `orderCount` read at the RECEIPT'S BLOCK (never Latest) and compared to
    `before_count + length successes` — anchored on the preview's success PATTERN, never on the
    preview's absolute ids
  - per-id `getOrderPacked` readback content-matched to the submitted order
  KNOWN LIMIT to record honestly (Phase 21 follow-up #5, PARTIALLY ADDRESSED): `verify_mined_order`
  compares the 4-field `VolOrder` record, so `unpack_vol_order_storage` discards tickSpacing
  (bits 104..127) and anything at >= 248 BEFORE the comparison.

SENDERS: orders go from `accounts.sender` (index 1) exactly as today. Swaps go from
  `accounts.deployer` (index 0). Do not converge them.

SC-5 REPLAY, and its honest limit: the same `RIG_SEED` against a FRESH rig reproduces the tick
  path, the drawn targetVegas and the minted order ids (a fresh rig starts at orderCount 0). It
  does NOT reproduce absolute timestamps — `t_0` is read from the chain head. Compare the TICK
  PATH and the `e3.tick` SERIES and the `orders` block; state the timestamp limit rather than
  quietly excluding it.
