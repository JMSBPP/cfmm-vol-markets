STRIDE = 12 seconds, a module-level constant in Sample.hs and RECORDED in the artifact.
  Correctness needs only >= 1 (the guard is an equality on the uint32 timestamp), but 12 is the
  mainnet block cadence, which keeps the oracle's sigma^2 window arithmetic in a realistic regime
  and is equally deterministic. Recording it means the question is answered by data, not by a
  constant someone has to go read.

SCHEDULE:  t_0 = chain_head_timestamp + stride        (read ONCE at driver start)
           t_k = t_0 + k * stride
  HONEST LIMIT, write it in the haddock: t_0 is chain-dependent, so absolute timestamps do NOT
  replay across rigs. `anvil --timestamp "$INIT_TS"` (added in 22-03) fixes the ORIGIN at
  1700000000 but the clock still advances with wall time from there, so a from-scratch rig gives a
  different t_0. What DOES replay from the recorded seed is the TICK PATH and therefore the
  `e3.tick` series; the schedule replays in SHAPE (t_k - t_0 = k*stride). The artifact records t_0
  so every offline check is written against the run's own origin.

SEED (SC-5, and a real gap today — offchain/app/Main.hs calls `createSystemRandom`, unseeded and
unrecorded):
  RIG_SEED holds a single decimal Word32. Unset -> draw one, PRINT it, and write it to the
  artifact. Either way `System.Random.MWC.initialize (V.singleton seed)`.
  `vector-0.13.2.0` is ALREADY in the build plan (mwc-random depends on it), so adding `vector` to
  build-depends introduces NO new package — 21-04's "no new dependency" property survives.
  Do NOT try to round-trip mwc-random's `Seed` through show/read: `Seed` derives
  (Eq, Show, Typeable) and has NO `Read` instance.

MID-RUN FAILURE POLICY: abort loud on the FIRST failure with the tx hash and the step index, AND
flush the partial artifact before exiting.
  Reason 1, the decisive one: G2 makes a corrupt series unrecoverable AND invisible. Once a bad
  timestamp lands, the oracle's window math is silently wrong for every subsequent step;
  complete-and-report-all would produce evidence that LOOKS fine and is not.
  Reason 2: it matches the codebase — `create_orders` already fails on the first bad receipt.
  Reason 3: the flush costs nothing and is the only thing that makes the failure debuggable.
  IMPLEMENTATION CONSTRAINT: `fail` inside a `Web3` action surfaces as an UNCAUGHT IOException,
  NOT as `runWeb3'`'s `Left` (documented in PriceSetter.Rpc and StochasticOrderGen.Rpc), and it can
  fire MID-FOLD after earlier transactions have mined. So the flush MUST be in the exception path —
  `Control.Exception.finally` in `Main`, over an `IORef` the fold appends to — not merely after a
  happy return.

WHAT MUST NOT CHANGE: `PriceSetter.Rpc.write_price` and `StochasticPriceGen.Rpc.run_price_gen`.
  Roadmap SC-1 and 22-CONTEXT both require the existing `write_price` / PriceSetterHook flow to
  stay available and unchanged — this driver is ADDED BESIDE it, never a replacement. `Main.hs`
  keeps calling both. `PriceSetterHook` now additionally serves as the tick -> sqrtPriceX96 oracle
  via `packSlot0For`, which is a new CONSUMER of it, not a change to it.
