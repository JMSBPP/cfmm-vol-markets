<objective>
The elision path: a hit returns the stored artifact and the solver is never spawned; a miss solves
once and persists; an abort persists NOTHING and still leaves a chronology row.

Purpose: STORE-08 is the sharpest trap in the phase. "A partial or failed run never becomes a cache
entry" makes ABSENCE the pass condition — it is green when the store is switched off, when the
connection is dead, when the table does not exist and when the insert path was never called. It is
the empty-log `grep -q` shape, which this repository has already been bitten by. **The only
instrument that fixes it is a POSITIVE CONTROL THAT LANDS, evaluated FIRST**: the same driver, the
same key, a `Produced` outcome, `entries == 1` from the store's own count — and only then each abort
variant driven separately with `entries == 0` and exactly one log row. "An exception was raised" and
"nothing was written" are different claims.

STORE-01 is a PAIR for the same reason: assert the returned artifact is the SEEDED bytes **B** (so a
path that re-solved and returned fresh bytes **B′** fails on the VALUE) AND that the call counter is
zero (so a path that solved and discarded fails too). Either alone is passable.

Output: `Store.Solver`, `Store.Cache`, and eight checks.
</objective>

  <action>
    Add `Store.Solver` and `Store.Cache` to the library's `exposed-modules` after `Store.Verify`.
    No new package.

    `Store.Solver` is one record and its haddock: the seam exists so a check can hand `decide` a
    solver that COUNTS its calls and returns bytes chosen to differ from the seeded ones — which is
    the only way "the solver was never spawned" can be observed without timing. State that timing is
    NOT the instrument, per the roadmap.

    `Store.Cache` is **THE ONE IO EDGE** of the store layer, the same way `Gams.Run` is the one edge
    of the solver layer. `decide` in order:
    1. `key_identity` / `content_key` — a refusal here is `Refused` and appends a
       `RefusedBeforeKey` log row with `re_key = Nothing`. **The key must be computed BEFORE the
       solver is consulted**; a design that solves first and keys afterwards can never elide.
    2. `store_lookup` on the triple. `Just` -> append a `Hit` row, return `Elided` carrying
       `sr_raw`. **This branch must not mention the solver, the verifier or the
       freshly-solved constructor** — STORE-04 is a structural claim about the hot path, and Nix
       shipped always-verify and removed it in 2.13 as broken.
    3. `Nothing` -> `solver_solve`. On `Produced`, `persist_produced` then a `MissSolved` row. On
       `Aborted`, an `aborted_*` row and NOTHING else.

    The identity is taken from the `Produced` outcome's own `ToolchainIdentity`; when the store is
    consulted before a solve there is no live identity, so `decide` takes the `KeyIdentity` as a
    parameter resolved by the caller through `key_identity`. Record in the haddock that this is why
    the signature carries a `KeyIdentity` and not a `RunRequest`: a `RunRequest` would put the run
    directory within reach of the key, which is 25-RESEARCH M3's zero-hit-rate failure.

    `Store.Cache` must name no reset, no truncate, no delete and no drop. Say so in the haddock by
    DESCRIBING the operations rather than spelling them — the scan in task 3 reads this file.
  </action>
