<objective>
The three exhibits whose pass condition is an ABSENCE, driven against a real server with the control
that makes each absence mean something.

Purpose: **STORE-08 is the sharpest trap in the phase.** "A partial or failed run never becomes a
cache entry" is green when the store is switched off, when the connection is dead, when the table
does not exist and when the insert path was never called — the empty-log `grep -q` shape this
repository has already been bitten by. The only instrument that fixes it is 24-06's: a POSITIVE
CONTROL THAT LANDS, evaluated FIRST, counted by the server itself. The same asymmetry applies to
quarantine: `quarantine_rows_after == 1` proves nothing without an AGREEING re-solve adding ZERO
rows, or the guard is satisfied by a quarantine that records everything.

**Decision of record, taken here:** the preimage is NOT stored in `model_run`. It is derivable from
the shock and the identity, and a digest recorded beside the thing it digests is the tautology this
repository has been bitten by (`Store.Types.volume_path_golden_sha256`'s haddock states the rule).
The capture records the computed preimage digest and the argv token list it describes, and the check
asserts the argv carries no per-run token. Record this decision and its reason in the summary.

**Decision of record #2, taken here — B3's resolution: the verifier's reachability guard is
RE-SCOPED, not routed around.** Plan 25-05 ships
`verification_is_reachable_only_from_its_own_entrypoint`, and this plan's quarantine exhibit needs
the verification path driven from `offchain/app/StoreConformance.hs` — a second importer inside a
scanned directory, which would redden a guard three waves after it was installed. The two
resolutions considered were (a) spawning the `store-admin` binary as a subprocess from the capture,
and (b) extending the guard's named set. **(b) is chosen**, for three reasons: the guard is already
written as a SET with reasons rather than as a count, precisely so it can be extended by NAME
instead of weakened; the invariant that actually carries STORE-04 is the `offchain/lib/` half — that
NOTHING on the hot path imports the verifier — and that half stays at ZERO, unweakened, in every
wave of this phase; and (a) would make the DB-only capture spawn a project binary it would then have
to resolve, which is the fragility plan 25-05's `STORE_ADMIN_BIN` mechanism exists to contain and
which buys nothing here, since a subprocess would exercise the same library code through one more
layer. Task 3 makes the extension with a written reason and a FRESH firing input; it does not
merely bump a number.

Output: three new observation blocks, a re-taken artifact, and six Tier-C checks — plus the guard
re-scope, with its own observation.
