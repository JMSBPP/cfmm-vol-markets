<objective>
The append-only run log, OBSERVED refusing — and the two facts that make a weaker design look
identical from Haskell.

Purpose, all MEASURED on a real PG 18.4 on 2026-08-17:
**(a)** `revoke update, delete on run_log from postgres` is a SILENT NO-OP against the role this
application actually connects as — the UPDATE landed and the row read back `TAMPERED` with no error.
**(b)** With the row trigger installed, `truncate run_log` **emptied the table with no error at
all**, because row-level triggers do not fire on TRUNCATE. **(c)** A superuser can `drop trigger` and
then update, which is why the trigger's PRESENCE IN THE LIVE CATALOGUE is asserted by name rather
than its behaviour alone. **(d)** `on conflict do nothing returning` returns NO ROW on conflict, so
the caller cannot tell "I wrote it" from "it existed"; `xmax = 0` returns `t` then `f`.

Every one of those is recorded here as a VALUE in the committed capture, including the negative one:
a REVOKE-only design must be visible as advertised-and-dead rather than inferred to be so.

Output: **four** new observation blocks, a re-taken artifact, and six Tier-C checks.

**(e) STORE-05's real subject had never been observed.** Plan 25-04 writes `store_pin` and
`store_reset` (`delete from model_run where not pinned`) into `Store.Postgres`, and NOTHING ran
them: `cabal test` exercises `Store.Memory` only, and no capture block touched either. The
47-row research map's Tier-C row `store_conformance_records_the_pin_column_and_its_default` was the
only row of the map no plan delivered. A fourth block, `pin_and_reset`, is added here rather than
recorded as a deviation, because "pinning survives retention" is exactly the claim whose Haskell
half cannot predict its SQL half: `Store.Memory` filters a map on a `Bool`, while the server runs a
`delete … where not pinned` against a column whose default this block also reads out of the live
catalogue.
