The schema half of the store: the append-only run log with BOTH triggers, the quarantine table, and
the lock-probe renumber that stops the identical defect 24-06 already paid for once.

Purpose: MEASURED on PG 18.4 today — `revoke update, delete on run_log from postgres` is a **silent
no-op**: the superuser UPDATE LANDED and read back `TAMPERED` with no error, and this application
connects as `postgres`. A `BEFORE UPDATE OR DELETE ... FOR EACH ROW` trigger refuses it loudly — and
then `truncate run_log` **emptied the table with no error at all**, because row-level triggers do not
fire on TRUNCATE. A second `BEFORE TRUNCATE ... FOR EACH STATEMENT` trigger closes it. STORE-06's
`reset` is precisely the operation a future author reaches for `truncate` to implement, which is why
the hole and the requirement meet here. **This is a deliberate deviation from the roadmap's implied
REVOKE-shaped guard and is recorded so it is not read as drift.**

Also MEASURED: `lock_probe_filename = "004_lock_probe.sql"` sorts BEFORE every plausible
`004_*.sql`, and `postgresql-migration` orders by FILENAME. This plan lands the first real `004` and
renumbers the probe **in the same task**, not after.
