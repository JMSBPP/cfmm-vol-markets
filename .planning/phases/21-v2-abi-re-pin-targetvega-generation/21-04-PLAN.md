THE DRAW LAW IS DECIDED. Do not re-open it; encode it.

    data VegaDraw
      = LogUniform
          { vega_min :: Integer   -- inclusive lower bound, raw L
          , vega_max :: Integer   -- inclusive upper bound, raw L
          }
      deriving (Eq, Show)

    vega_min = 10^18
    vega_max = 10^21

WHY THOSE TWO NUMBERS, exactly (this belongs in the type's haddock so the next reader does not
re-derive it):
  - `targetVega` is DeltaQ_v*, RAW UNISWAP-L units — dimension (ii) of `notes/UNITS_AND_SCALES.md`
    section 2. NOT X96, NOT WAD, NOT collateral. A unit slip is invisible on-chain (any u96 stores
    fine) and only surfaces as nonsense downstream.
  - Instantiate the standard v3 relation `amount1 = L * (sqrt(P) - sqrt(Pa))` on THE RIG'S OWN POOL:
    `initTick = 0` so `P = 1`, both `MinimalToken`s are 18 decimals. Depositing one whole token
    (10^18 wei) of token1 over a symmetric width `w` ticks about tick 0 gives
    `L = amount1 / (1 - 1.0001^(-w/4))`:

        full range (+/-887272)  ->  L = 1.000e18
        w = 20 000              ->  L = 2.542e18
        w = 1 000               ->  L = 4.050e19
        w = 20                  ->  L = 2.001e21

    So [1e18, 1e21] is exactly "one whole 18-decimal token, from full range down to a ~20-tick
    concentrated band" — the concentrated-liquidity regime this instrument targets.
  - Headroom: u96 max = 7.923e28, so 1e21 leaves 7.9e7x. `UNITS_AND_SCALES.md` section 2's
    "realistic pool liquidity 1e18-1e21, >=1e7x headroom" claim is thereby GROUNDED, not corrected.
  - Bit-lengths: 1e18 = 2^59.8, 1e21 = 2^69.8 — the band occupies bit-lengths 60..70 of a 96-bit
    field.
  - SHAPE: Heimbach, Schertenleib, Wattenhofer, "Risks and Returns of Uniswap V3 Liquidity
    Providers", ACM AFT 2022, arXiv:2205.08904, measures real v3 positions and reports the MEAN
    position size around TEN TIMES the MEDIAN (rising to 100x in 2022) — a strongly right-skewed,
    log-scale quantity. Linear-uniform on [1e18, 1e21] would put 90% of draws in [1e20, 1e21] and
    essentially never sample the full-range end; a fixed constant exercises one bit-length. Both
    are rejected. Log-uniform is the scale-invariant / maximum-entropy law on a positive quantity
    whose only established feature is its order-of-magnitude range, and it commits to no fitted
    parameter no source gives for our pool.

THE HONEST LIMIT — put this in the code comment, do NOT let it weaken the implementation: no
source, local or academic, specifies a SAMPLING LAW for a variance-instrument target vega in raw L
units. The evidence pins the band exactly and pins the quantity as log-scale rather than
linear-scale; log-uniform is the most defensible default given both, and it is defensible BECAUSE
it adds nothing beyond them. If a later phase measures the rig pool's actual L distribution,
`VegaDraw` gains a second constructor and nothing else changes — which is exactly why CONTEXT
locked it as a one-constructor sum type, mirroring `ArrivalProcess` and `ProcessType`.

THE IMPLEMENTATION, verified by compiling and running a probe against this project's package
environment (GHC 9.10.3, mwc-random 0.15.3.0):

    draw_target_vega :: GenIO -> VegaDraw -> IO Integer
    draw_target_vega gen (LogUniform lo hi) = do
      u <- uniformR (0, 1) gen :: IO Double
      let v = round (fromIntegral lo * (fromIntegral hi / fromIntegral lo) ** u) :: Integer
      if v >= max 1 lo && v <= min hi (2 ^ (96 :: Int) - 1)
        then pure v
        else fail ("targetVega draw out of band: " ++ show v
                    ++ " not in [" ++ show lo ++ ", " ++ show hi ++ "]")

THE STATIC-ORDERS TENSION IS RESOLVED — do not re-litigate it. `StochasticOrderGen` today holds
`orders :: [VolOrder]` and `run_order_gen` takes the first N. Once `VolOrder` carries
`target_vega`, "the generator draws it" collides with "the orders are supplied ready-made". The
DECIDED shape is a partial type:

    data OrderShape = OrderShape
      { shape_vol_target  :: Quantity
      , shape_range_width :: Quantity
      , shape_skew        :: Quantity
      } deriving (Eq, Show)

The generator BUILDS `VolOrder`s by attaching a drawn `target_vega`. The rejected alternative —
keeping `orders :: [VolOrder]` and overwriting each `target_vega` — would force `Sample.hs` to
supply a placeholder that is silently discarded: a value that looks meaningful and is not, which is
the same defect class as a stale address literal. The field prefixes (`shape_`) exist because
`Sample.hs` imports both this module and `VolOrder.Types`, and unprefixed names would collide.

Existing code that must keep working: `run_order_gen`'s guard
`batch_count > length (orders config)` fails loudly with a named message; `chunk max_batch` with
`max_batch = 128`; `create_orders` per chunk. `run_order_gen` ALREADY takes `gen :: GenIO`, so the
draw needs no signature change to that function.
