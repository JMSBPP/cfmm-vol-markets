THE FOUR CASES TO CAPTURE. Each is
`cast call "$MGR" "$(cast calldata 'create_orders(uint256,uint256[])' N '[w...]')" --rpc-url "$RPC"`.

  - `N0_empty`, N = 0, tuples `[]` — the 64-byte empty return. v4.0's exit record names this "the
    single clause in the return contract most likely to break StochasticOrderGen", and it is
    invisible on-chain.
  - `N1_success`, N = 1, `(strike=12345, width=600, skew=77, targetVega=10^18)` — one valid V2 tuple
    carrying a real targetVega in raw L units.
  - `N2_success_then_fail`, N = 2, `(12345, 600, 77, 10^18)` then `(999, 7, 65535, 10^18)` — mixed.
    `skew = 65535` is the ONLY client-passing / contract-rejected input
    (`spread_tick_assimetry_is_complete` accepts [1, 65534]), so this exercises best-effort skip
    semantics live.
  - `N1_dirty_vega`, N = 1, `(12345, 600, 77, 2^96)` — a targetVega ONE ABOVE the u96 bound. This is
    the V2-specific silent-skip case: it must come back `(false, 0)`, INDISTINGUISHABLE from a
    business rejection. Capturing it is the evidence for why the client-side `in_range 96` guard in
    `pack_vol_order_input` exists at all.
