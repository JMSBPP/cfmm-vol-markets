## 5. Architecture Patterns

### 5.1 Recommended layout

```
offchain/rig/
├── deploy-rig.sh          # owns anvil; runs the 4 scripts; writes rig-manifest.json
├── rig-pins.json          # COMMITTED: signatures + selectors + topic0s (static)
├── rig-manifest.json      # GITIGNORED: per-deploy addresses + chainId + ref metadata
└── import-paths.txt       # the explicit path list the import + pin file both read
offchain/lib/Rig/
└── Manifest.hs            # aeson records + loader; exposed-module in the library stanza
offchain/test/
└── Main.hs                # pin tests (currently a stub: "Test suite not yet implemented.")
```

### 5.2 Pattern: split manifest with ONE merged view for consumers

CONTEXT locks the split (static committed / addresses gitignored). Keep the Haskell surface a
*single* value so no caller has to know about the split:

```haskell
-- offchain/lib/Rig/Manifest.hs
data RigPins = RigPins
  { pinSelectors :: Map Text PinEntry   -- key: "create_order", value: {signature, selector}
  , pinTopics    :: Map Text PinEntry   -- key: "VolOrderCreated", value: {signature, topic0}
  } deriving (Eq, Show)

data RigAddresses = RigAddresses
  { rigChainId       :: Integer
  , rigDeployer      :: Text
  , rigSender        :: Text
  , rigContracts     :: Map Text Text   -- "VolOrderManagerMod" -> "0x…"
  , rigPoolId        :: Maybe Text
  , rigGeneratedFrom :: Text            -- the develop ref recorded at import time
  } deriving (Eq, Show)

data Rig = Rig { rigPins :: RigPins, rigAddrs :: RigAddresses }

load_rig :: FilePath -> FilePath -> IO Rig     -- eitherDecodeFileStrict, `either fail pure`
```

**Path resolution:** take it from an env var with a fixed relative default —
`RIG_MANIFEST` / `RIG_PINS`, defaulting to `offchain/rig/rig-manifest.json` and
`offchain/rig/rig-pins.json`. A CLI-arg-only design forces every `cabal run` demo to pass flags;
a fixed-path-only design breaks when run from another cwd. Env-with-default is the smallest
thing that satisfies "loud failure, never a silent default": if the file is missing, `fail` with
the resolved path in the message and the instruction to run `offchain/rig/deploy-rig.sh`.

**Anti-pattern:** do NOT give the records `Maybe`-defaulted address fields or a `FromJSON`
instance with `.:?` fallbacks for contract addresses. A missing address must be a decode failure.
Use `.:` for everything the drivers need.

### 5.3 Pattern: pin tests recompute from the interface files' signature strings

The interface `.plk` files carry a machine-parseable convention — **verified across all six files**:

```
// signature:: create_order(uint88,uint24,uint16,uint96)   (strike, width, skew, targetVega;
const SELECTOR_CREATE_ORDER = 0x98d950ec;

// event:: VolOrderCreated(uint256 indexed orderId, uint88 strike, uint24 width, uint16 skew, uint96 targetVega)
const TOPIC0_EVENT_VOL_ORDER_CREATED = 0x18bd4d46…;
```

The recomputation is:

```haskell
import Crypto.Ethereum.Utils (keccak256)   -- web3-crypto
import qualified Data.ByteString as BS
import qualified Data.ByteString.Char8 as C8

selector_of :: String -> BS.ByteString
selector_of = BS.take 4 . keccak256 . C8.pack

topic0_of :: String -> BS.ByteString
topic0_of = keccak256 . C8.pack
```

**All five SC-4 values were recomputed here with `cast` and MATCH** (this is the ground truth the
Haskell test must reproduce):

| Signature | Computed | Matches interface file |
|---|---|---|
| `create_order(uint88,uint24,uint16,uint96)` | `0x98d950ec` | ✅ |
| `create_orders(uint256,uint256[])` | `0x81357911` | ✅ |
| `writeTimepoint(uint32,int24)` | `0xb09b2297` | ✅ |
| `VolOrderCreated(uint256,uint88,uint24,uint16,uint96)` | `0x18bd4d460f8957f6b903aec33a3229ee1bf02b6e303c5178c5aa49a70b9de4e6` | ✅ |
| `TimepointWritten(bytes32,uint32,int24,uint88,int24,int56)` | `0x44d3c76a584327df3a91e46e185e97959195c01202945078eebb23b19c161415` | ✅ |

Also verified (available for a wider pin set): `orderCount()`=`0x2453ffa8`,
`getOrderPacked(uint256)`=`0xa9bcabc1`, `initializeTWAP(uint32,int24)`=`0xed64c40a`,
`getTimepointPacked(uint16)`=`0xbf15969d`, `lastIndex()`=`0xf3f6f0d7`,
`WindowChanged(bytes32,uint32)`=`0x046630ea…`,
`FeeConfigurationChanged(bytes32,uint16,uint16,uint32,uint32,uint16,uint16,uint16)`=`0x0b849672…`,
`FeeApplied(bytes32,uint88,uint24)`=`0x25ea110a…`.

**Two normalization rules the parser MUST implement** (both are real, both are in the files):

1. **Event comments carry parameter names and `indexed`; topic0 is keccak of the CANONICAL form.**
   `VolOrderCreated(uint256 indexed orderId, uint88 strike, …)` must be normalized to
   `VolOrderCreated(uint256,uint88,uint24,uint16,uint96)`. But `DynamicFeeHookInterface.plk` line 35
   already writes the canonical form: `TimepointWritten(bytes32,uint32,int24,uint88,int24,int56)`.
   **The parser must handle both** — strip `indexed`, strip trailing identifiers, strip whitespace,
   idempotently.
2. **Signatures wrap across lines.** `RealizedVolatilityInterface.plk` lines 61–62 continue
   `TimepointWritten(...` onto a second `//` line; `VolOrderManagerInterface.plk` line 13 has
   trailing prose *containing parentheses* on the same line and continuing onto line 14. A naive
   single-line regex will silently truncate a signature and compute a WRONG hash that still
   "looks like" a topic0. **Parse by balanced-paren accumulation across continuation `//` lines,
   and prove the parser falsifiable** by feeding it the multi-line `TimepointWritten` block and
   asserting it produces `0x44d3c76a…` — a truncation would not.

**Prefer parsing the imported files over hand-listing signatures in the test.** SC-4's whole point
("a consumption check, not a re-derivation") is defeated if the test hardcodes the signature
strings; the *file* must be the input.

### 5.4 Pattern: address extraction from `run-latest.json`

**MEASURED shape** (from the existing `broadcast/VolOrderManager.s.sol/31337/run-latest.json`,
which is itself a `plankDeployFFI` deploy):

```json
{ "chain": 31337, "commit": "443070a",
  "transactions": [ { "transactionType": "CREATE", "contractName": null,
                      "contractAddress": "0x5fbdb2315678afecb367f032d93f642f64180aa3",
                      "additionalContracts": [] } ],
  "receipts": [ { "status": "...", "contractAddress": "...", "logs": [...] } ] }
```

Two extraction rules, and the second is the trap:

- **Plank FFI deploys (`plankDeployFFI`) land in `.transactions[].contractAddress` with
  `contractName: null`.** MEASURED — so scripts 1–3 are simple: take the first
  `transactionType == "CREATE"` in that script's `run-latest.json`. You **cannot** key on
  `contractName`; it is null for every Plank module.
- **`DeployDynamicFeeHook` deploys the hook through a raw `.call` to CREATE2_DEPLOYER**, not
  `new X{salt:…}`. The existing `PriceSetterHook` broadcast — which uses `new X{salt:…}` — shows
  `transactionType: "CREATE2"` with a populated `contractName`/`contractAddress`. A raw call to
  the proxy is recorded as `transactionType: "CALL"` to `0x4e59b448…` with the created contract
  in `additionalContracts[]`. **Confidence MEDIUM (predicted, not observed here).** The generator
  must handle both, and the console cross-check must be capable of *correcting* it — which is
  exactly why CONTEXT mandated the cross-check.
- `PoolManager` and the two `MinimalToken`s are ordinary `new` CREATEs with real `contractName`s.

Suggested `jq` for the simple case:

```bash
jq -r '[.transactions[] | select(.transactionType=="CREATE")][0].contractAddress' \
   broadcast/DeployVolOrderManagerMod.s.sol/31337/run-latest.json
```

and for the hook:

```bash
jq -r '(.transactions[] | select(.contractName=="PoolManager") | .contractAddress),
       ([.transactions[].additionalContracts[]? | select(.transactionType=="CREATE2") | .address][0])' \
   broadcast/DeployDynamicFeeHook.s.sol/31337/run-latest.json
```

### 5.5 Pattern: `deploy-rig.sh` owns anvil

```bash
#!/usr/bin/env bash
set -euo pipefail
# 1. kill stale anvil (pkill -f 'anvil' or lsof on 8545), wait for port release
# 2. anvil --silent & ANVIL_PID=$!; trap 'kill $ANVIL_PID' EXIT (only on failure paths — the rig
#    must SURVIVE the script for the drivers to use, so prefer a --keep-alive default and an
#    explicit `deploy-rig.sh --stop`)
# 3. poll `cast block-number --rpc-url local` until it answers (never a fixed sleep)
# 4. rm -rf broadcast/Deploy*.s.sol   # stale run-latest.json from a previous rig is the
#                                     # single most dangerous input to the manifest generator
# 5. run the four forge script commands, tee each to a per-script log
# 6. build rig-manifest.json with jq from the four run-latest.json files
# 7. cross-check every address against the tee'd console log (case-insensitive!) — mismatch = exit 1
# 8. liveness probes (see §11)
```

**Step 4 is not optional.** If script 3 fails, its `run-latest.json` from the *previous* run
remains on disk and the generator will happily emit a stale address that the console cross-check
— reading the *current* log — would catch, but only if the cross-check is wired. Deleting first
makes the failure mode "file not found" instead of "wrong address".

### 5.6 Anti-patterns

- **Deriving addresses from anvil's deterministic nonce sequence** (`0x5FbDB231…` is "the first
  contract deployed by account 0"). It is how `Sample.hs`'s literals were obtained and it is
  exactly the rot this phase exists to kill. CONTEXT forbids chain-scanning re-derivation; nonce
  arithmetic is the same sin in cheaper clothes.
- **Re-typing any imported value.** Every selector/topic0 in `rig-pins.json` must be *generated*
  from the imported `.plk` files by a script, then committed. Typing them into JSON by hand
  reintroduces the `0xa8892769…` failure mode one layer down.
- **A pin test that hardcodes signature strings.** See §5.3.
- **Editing `foundry.toml`, `remappings.txt`, `Makefile`, or `src/**` content.** Imports of
  plank's files are allowed; edits are not. §2.4 confirms no config edit is needed.

### 6.2 The scope question the plan MUST settle explicitly

CONTEXT says the grep check "needs no whitelist". Taken literally over `offchain/**` it will fail
on `offchain/spec/types.md` — 13 hits, all inside a pasted RPC transcript, including an anvil
private key. Three honest options, in preference order:

1. **Scope the check to `offchain/**/*.hs` plus `offchain/rig/*.sh`** (the executable surface —
   which is what "the manifest cannot be quietly bypassed" actually means), and say so in the
   check's own header comment. *Recommended.*
2. Keep `offchain/**` scope and redact the transcript in `types.md` (it is this workstream's file,
   and it is already modified in the working tree). Costs a doc edit; gains a stricter check.
3. Keep `offchain/**` and whitelist `types.md` — explicitly contradicts CONTEXT's "no whitelist".

Pick 1 or 2 in the plan and record why; do not let the executor discover this at check-authoring
time and silently pick 3.

Patterns to use (word-boundary anchored so a 64-hex topic0 does not also match the 40-hex rule):

```bash
grep -rnE '0x[0-9a-fA-F]{64}\b' <scope>   # topic0 / hash
grep -rnE '0x[0-9a-fA-F]{40}\b' <scope>   # address
grep -rnE '0x[0-9a-fA-F]{8}\b'  <scope>   # selector (also catches Decode.hs:32's truncated topic0)
```

Where the check runs: **inside `deploy-rig.sh` is the wrong place** (it would only run when the
rig is deployed). Put it in the cabal test-suite as a test that shells out to `grep`, so it runs
on every `cabal test` and can be a Phase-gate command. Add it to `deploy-rig.sh` as a *courtesy*
final step if desired.

### 6.3 Sequencing trap: `Decode.hs`'s `topic_order_created`

Phase 20 purges literals; Phase 21 (RPIN-04) re-pins the topic0 and must *demonstrate the pin test
going RED against `0xa8892769…`*. If Phase 20 deletes the constant outright, Phase 21's
falsifiability demonstration loses its subject.

**Prescription:** Phase 20 moves `topic_order_created` to read from `rig-pins.json` (the V2 value
`0x18bd4d46…`, derived from the imported interface file) and leaves `decode_order_created`'s
*structure* alone — the 3-topic/5-word v1 log layout stays broken-but-untouched until Phase 21.
Record `0xa8892769…` (and the v1 `0x6a5dc726…`) in the pin file/plan as RETIRED values Phase 21
must prove are rejected. This satisfies SC-3 (no literal outside the manifest) without stealing
Phase 21's work or its evidence.

## 7. Common Pitfalls

### 7.1 `forge build` fails today — `node_modules` is a hard dependency (MEASURED)

**What goes wrong:** any `forge script` invocation dies before touching the chain.
**Observed, this worktree, 2026-07-31:**

```
Error (6275): Source "node_modules/@cryptoalgebra/volatility-oracle-plugin/contracts/
VolatilityOraclePluginImplementation.sol" not found  --> test/MarketStatisticsTest.t.sol:8:1
```

**Root cause:** `foundry.toml` remaps `@cryptoalgebra/...` into `node_modules/`, four tracked
`.sol` files import it (`test/MarketStatisticsTest.t.sol`,
`test/market_state_measurements/RealizedVolatility.diff.t.sol`, `test/mocks/AlgebraVolatilityKernelMock.sol`,
`test/types/pos_spec/VolRangeWidth.t.sol`), and `node_modules/` is gitignored and absent here.
`forge script` compiles the whole project including `test/`.
**Fix:** `npm ci --ignore-scripts` — the same step plank's `develop-gate.yml` runs, with the
in-file comment "node_modules became a HARD forge dependency with the premium port".
**Warning sign:** `ParserError: Source "node_modules/..." not found`.
**Plan action:** a Wave-0 preflight task that runs `npm ci --ignore-scripts` and then asserts
`forge build` exits 0 — BEFORE any import, so a post-import failure is unambiguously attributable
to the import.

### 7.2 Console addresses are checksummed; broadcast JSON is lowercase

`run-latest.json` stores `0x5fbdb2315678afecb367f032d93f642f64180aa3` (all lowercase — measured);
`forge`'s `console.log(string,address)` renders EIP-55 mixed case. **Confidence MEDIUM on the
render format, HIGH on the JSON format.** A naive string `==` cross-check will fail on every
address. **Normalize both sides with `tr 'A-Z' 'a-z'` before comparing** — unconditionally, so the
check is correct under either rendering.

### 7.3 A signature parser that reads one line computes a plausible-but-wrong hash

Covered in §5.3. The danger is that the wrong value *is* a valid 32-byte hash, so nothing looks
broken — it just never matches a real log. Mitigate with the multi-line `TimepointWritten`
regression case.

### 7.4 `IMarketStateSocket.plk` breaks naive glob parsers

Seven `const NAME =` lines with no values. §2.1.

### 7.5 Importing the V2 `src/` closure will turn the local Foundry test suite RED

`test/pos_spec/*.t.sol` on this branch exercises the **v1** 3-arg `create_order`. After importing
the V2 modules these tests will fail *at runtime* (not at compile — `.plk` files are never seen by
solc, so `forge build` and therefore `forge script` are unaffected). This is expected and is NOT
this workstream's to fix: `test/` belongs to the Solidity-testing session per `CLAUDE.md`.
**Plan action:** measure `forge test` BEFORE the import and AFTER, record both counts in the
summary, attribute every new red to the V2 import, and report — do not repair. (This repo's own
v4.0 exit record shows four prior instances of a criterion that was unsatisfiable because a
measured baseline was assumed rather than taken.)

### 7.6 Stale `broadcast/run-latest.json` silently poisons the manifest

§5.5 step 4. A failed script leaves the previous run's file in place.

### 7.7 `INIT_TS = 0` silently skips the seed

`DeployRealizedVolatilityMod` only calls `initializeTWAP` when `initTs != 0`; the console prints
`seeded : false` and the script still exits 0. SC-2's "NONZERO packed timepoint" would then fail
for a *configuration* reason that looks like a deployment failure. `deploy-rig.sh` must export a
nonzero `INIT_TS` and assert the `seeded : true` line. Good news for the liveness probe:
`Timepoint.plk` puts `OFF_INITIALIZED = 240`, so a seeded timepoint's packed word is nonzero
**regardless of the tick value** — `INIT_TICK` may safely be 0.

### 7.8 The two different `INIT_TICK`s

`DeployRealizedVolatilityMod` reads `INIT_TICK` from env; `DeployDynamicFeeHook` has an unrelated
`int24 constant INIT_TICK = 0` that is *not* env-read. Exporting `INIT_TICK` does not move the
hook's pool. Do not document them as one knob.

### 7.9 `--tc` on exactly one script

`DeployDynamicFeeHook.s.sol` declares two contracts (`DeployDynamicFeeHook`, `MinimalToken`);
without `--tc DeployDynamicFeeHook` forge cannot pick a target. The other three files are
single-contract and must NOT get a `--tc` (harmless but noise).

### 7.10 `git checkout <ref> -- src/` would import 27 unrelated files

§2.3. Use an explicit path list.

## 8. Don't Hand-Roll

| Problem | Don't build | Use instead | Why |
|---|---|---|---|
| keccak-256 in Haskell | a Keccak implementation, or a `Data.Hashable`-based approximation | `Crypto.Ethereum.Utils.keccak256` (`web3-crypto`, already in the resolved install-plan; wraps `crypton`'s `Keccak_256`) | Keccak ≠ SHA3-256 padding; getting it subtly wrong yields hashes that look fine and never match |
| ABI selector computation | manual `keccak(sig)[:4]` byte slicing scattered per call site | one `selector_of :: String -> ByteString` helper + `cast sig` as the independent cross-check | one implementation, one place to be wrong; `cast` gives a second encoder for free (the v4.0 milestone's strongest evidence pattern) |
| JSON parse/serialize | bespoke string building in bash or Haskell | `jq` (write side) + `aeson` (read side) | escaping and number formatting are where hand-rolled JSON dies; both are already present |
| Extracting deploy addresses | regexing forge's human-readable stdout as the primary source | `broadcast/**/run-latest.json` via `jq`, console as cross-check | CONTEXT-locked, and forge's stdout formatting is not a stability contract |
| Deriving contract addresses | `CREATE` nonce arithmetic / `cast compute-address` | the broadcast record | see §5.6 |
| Waiting for anvil | `sleep 2` | poll `cast block-number --rpc-url local` in a bounded loop | fixed sleeps are the classic CI flake |
| Anvil accounts | hardcoding `0xf39Fd6…` / `0x709979…` | `cast wallet address --mnemonic "$ANVIL_MNEMONIC" --mnemonic-index N` | hardcoding is precisely the literal class being purged |

**Key insight:** every value this phase touches already exists in a machine-readable artifact
produced by a tool that is already installed. The entire phase is *plumbing between existing
artifacts*; any line of code that *computes* a value the toolchain already emits is a future
staleness bug.

import Crypto.Ethereum.Utils (keccak256)
import qualified Data.ByteString      as BS
import qualified Data.ByteString.Char8 as C8

assert_selector :: String -> BS.ByteString -> IO ()

### 9.6 Liveness probes (SC-2)

```bash
# Source: selectors recomputed with `cast sig` above; getters confirmed DISPATCHED by reading
# RealizedVolatilityMod.plk's dispatch chain (SELECTOR_GET_TIMEPOINT_PACKED / _LAST_INDEX present).
cast call "$VOM" "orderCount()(uint256)" --rpc-url local            # answers 0 on a fresh rig
IDX=$(cast call "$RVM" "lastIndex()(uint16)" --rpc-url local)
PACKED=$(cast call "$RVM" "getTimepointPacked(uint16)(uint256)" --rpc-url local "$IDX")
[ "$PACKED" != "0" ] || { echo "RealizedVolatilityMod seed FAILED (packed timepoint == 0)"; exit 1; }
```

Note: `orderCount()` returning `0` on a fresh rig *is* a valid liveness signal only because a
call to an empty address returns empty returndata and `cast` errors rather than decoding `0` —
but that is fragile reasoning. **Stronger:** assert `cast code "$VOM" --rpc-url local` has length
> 2 AND `orderCount()` decodes, which together rule out the zero-length-bytecode silent failure
SC-2 names explicitly.

   contract is "an independent second source", not a particular format.
