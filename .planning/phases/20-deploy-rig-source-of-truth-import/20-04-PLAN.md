  <action>
Write `offchain/rig/generate-pins.sh` (`chmod +x`). It reads the six imported interface `.plk`
files and WRITES `offchain/rig/rig-pins.json`. Not one hex value in the output may appear as a
literal in the script — every selector and topic0 is computed by `cast` from a signature string the

**Parsing.** The convention (research §5.3, verified across all six files):

    // signature:: create_order(uint88,uint24,uint16,uint96)   (strike, width, skew, targetVega;
    const SELECTOR_CREATE_ORDER = 0x98d950ec;

    // event:: VolOrderCreated(uint256 indexed orderId, uint88 strike, uint24 width, uint16 skew, uint96 targetVega)
    const TOPIC0_EVENT_VOL_ORDER_CREATED = 0x18bd4d46…;

Two normalization rules, BOTH real, BOTH present in the files, both mandatory:

1. **Balanced-paren accumulation across continuation `//` lines.** Signatures WRAP.
   `RealizedVolatilityInterface.plk` lines 61-62 continue `TimepointWritten(...` onto a second
   `//` line; `VolOrderManagerInterface.plk` line 13 carries trailing prose *containing
   parentheses* on the same line and continues onto line 14. Start at the `signature::`/`event::`
   marker, accumulate until the parenthesis opened by the signature is CLOSED, appending
   continuation `//` lines, and discard anything after that closing paren. A single-line regex
   silently truncates and computes a wrong hash that still looks like a hash (research §7.3).
2. **Canonicalise the argument list.** Strip `indexed`, strip trailing parameter identifiers, strip
   all whitespace: `VolOrderCreated(uint256 indexed orderId, uint88 strike, …)` →
   `VolOrderCreated(uint256,uint88,uint24,uint16,uint96)`. The rule must be IDEMPOTENT:
   `DynamicFeeHookInterface.plk` line 35 already writes the canonical form
   `TimepointWritten(bytes32,uint32,int24,uint88,int24,int56)`, and running the normaliser over it
   must leave it unchanged.

**Skip valueless consts DELIBERATELY.** `IMarketStateSocket.plk` is seven `const NAME =` lines with
no values and no terminators. The parser must skip any `const X =` line with no hex value on the
right, and the script must PRINT how many such lines it skipped and in which file, so the exclusion
is a recorded decision rather than a silent one.

**Computation.** For each parsed pair, compute — never read the file's own hex as the answer:

    sel=$(cast sig "$SIGNATURE")                       # 0x + 8 hex
    top=$(cast keccak "$SIGNATURE")                    # 0x + 64 hex

then **assert the computed value equals the `const`'s declared value in the same file**, and abort
with a loud diff if not. The declared value is the CROSS-CHECK, the computed value is what gets
written. A disagreement means either the parser is wrong or the interface file is wrong — both are
findings, neither is something to paper over by preferring one side.

**Naming.** Key `selectors` by the function name (`create_order`, `create_orders`,
`writeTimepoint`, `orderCount`, `getOrderPacked`, `initializeTWAP`, `getTimepointPacked`,
`lastIndex`, …) and `topics` by the event name (`VolOrderCreated`, `TimepointWritten`,
`WindowChanged`, `FeeConfigurationChanged`, `FeeApplied`, …) — take the names from the parsed
signature itself, not from the `const` identifier. Emit EVERY pin the files declare; do not
hand-pick a subset. Research §5.3 lists 13 known values, of which these five are SC-4's named
targets and are the ones you can check against a full literal:

    create_order(uint88,uint24,uint16,uint96)                      -> 0x98d950ec
    create_orders(uint256,uint256[])                               -> 0x81357911
    writeTimepoint(uint32,int24)                                   -> 0xb09b2297
    VolOrderCreated(uint256,uint88,uint24,uint16,uint96)           -> 0x18bd4d460f8957f6b903aec33a3229ee1bf02b6e303c5178c5aa49a70b9de4e6
    TimepointWritten(bytes32,uint32,int24,uint88,int24,int56)      -> 0x44d3c76a584327df3a91e46e185e97959195c01202945078eebb23b19c161415

The other eight (`orderCount()`=`0x2453ffa8`, `getOrderPacked(uint256)`=`0xa9bcabc1`,
`initializeTWAP(uint32,int24)`=`0xed64c40a`, `getTimepointPacked(uint16)`=`0xbf15969d`,
`lastIndex()`=`0xf3f6f0d7`, and the topic0s for `WindowChanged`, `FeeConfigurationChanged`,
`FeeApplied`) are recorded in the research only in TRUNCATED form for the 32-byte ones — do not
expand a truncated value from memory. Let the generator produce them and let the in-file `const`
cross-check confirm them.

**The `retired` block.** Populate it from evidence, not recall. Include:
  - `create_order_v1`: `0x6501fe94` — the v1 selector, which 20-02 already asserted survives in the

    line 24, which is where the rot lives. Read it from that file, do not type it.
  - Any other value the imported files mark `RETIRED` — parse those too.
Do NOT invent a full 64-hex expansion of the truncated `0x6a5dc726…` that appears in the research;
if it is not present verbatim in a source file, it does not go in the file.
The `retired` block is data for plan 20-05's falsifiability test. It is NOT part of `selectors`/
`topics` and must never be iterated by the pin check as if it were a live pin — put that sentence
in the JSON as a `"_note"` key inside `retired`, or in the generator's header comment, so the
distinction is written down where the next reader will see it.
