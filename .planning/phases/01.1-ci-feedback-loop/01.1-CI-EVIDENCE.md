## The persistent-self-hosted question, answered from these runs

The ROADMAP's open question:

> Pinning Foundry on a *persistent self-hosted* runner is not the hosted-container problem —
> `foundry-rs/foundry-toolchain@v1` vs an explicit `foundryup --version`, tool-cache behaviour, and
> collision with the system `forge` already installed there. Do not assume the hosted recipe
> transfers.

### `which -a forge`, identical in both runs

Run 1:

    L1595: /home/jmsbpp/.foundry-pins/v1.5.1/bin/forge
    L1596: /home/jmsbpp/.foundry/bin/forge
    L1597: /home/jmsbpp/.foundry/bin/forge

Run 2:

    L1529: /home/jmsbpp/.foundry-pins/v1.5.1/bin/forge
    L1530: /home/jmsbpp/.foundry/bin/forge
    L1531: /home/jmsbpp/.foundry/bin/forge

**The pinned binary won, and the box's own forge was never touched.** There WAS a pre-existing
system forge at `/home/jmsbpp/.foundry/bin/forge` — twice on `PATH`, so the runner's environment
already had a duplicate entry before CI arrived. The `$GITHUB_PATH` prepend put
`.foundry-pins/v1.5.1/bin` ahead of both. `forge --version` resolved to the pinned binary in both
runs, and neither run wrote into `$HOME/.foundry`.

This is not a subtlety — it is the whole reason `foundry-rs/foundry-toolchain@v1` was rejected
during planning. That action installs into `os.homedir()/.foundry`, i.e. exactly the directory the
box's human-installed forge lives in. Using it would have had every unattended push build silently
rewrite the machine's default toolchain. The plan reasoned this; run 1 **measured** it. foundryup
itself said so out loud, unprompted:

    L1541: There are multiple binaries with the name 'forge' present in your 'PATH'.
    L1544: You may need to run 'rm /home/jmsbpp/.foundry/bin/forge' or move '/home/jmsbpp/.foundry-pins/v1.5.1/bin'

That advice is correct for a workstation and wrong for this runner. Declining it is the design.

### The four install-mechanism unknowns, each closed by run 1

| Unknown (from the plan) | Answer, from the run |
|---|---|
| Outbound access to `raw.githubusercontent.com` and the Foundry release host? | **YES.** `L1501: foundryup-init: binary verified ✓` and `L1502: foundryup-init: installing foundryup to /home/jmsbpp/.foundry-pins/v1.5.1/bin...` — the installer downloaded, attested and verified. No `curl: (6)`/`(7)`/`(35)`. |
| Is `flock` present? | **YES.** The step is `set -euo pipefail` with `flock 9` before the install branch, and it reached the download. No `flock: command not found`. |
| Is `--install` the right foundryup flag? | **YES.** `L1531: foundryup: binaries not found or do not match expected hashes, downloading new binaries` — the flag parsed and drove a real install. No `unknown option`. |
| Does `v1.5.1` actually build to `b0a9dd9…`? | **YES.** `L1539: foundryup: use - forge 1.5.1-v1.5.1 (b0a9dd9ced 2025-12-19T14:07:55.455914129Z)`, and `L1534: foundryup: forge verified ✓`. The pin's premise holds; no escalation needed. |

Total cold install cost: **19 s** (step 4, `19:19:35Z → 19:19:54Z`). Warm cost: **0 s** (run 2).

### Conclusion on the open question

**The mechanism chosen in plan 03 worked exactly as reasoned, and the reasoning was load-bearing
rather than decorative.** A pin-keyed directory (`$HOME/.foundry-pins/$FOUNDRY_VERSION`), a
`flock`-serialized install, a stamp file written only after the commit assertion, and a
`$GITHUB_PATH` prepend give this persistent runner a pinned toolchain **without mutating the shared
`$HOME/.foundry` the box's human owner installed**. Both runs resolved `b0a9dd9…`; both left the
system forge in place; the second run cost nothing because the stamp made it a no-op, while still
re-asserting the pin in the stamp step. The hosted recipe (`foundry-toolchain@v1`) would have
collided with the system install on the very first push — `which -a forge` is the proof that the
collision was real and was avoided, not hypothetical.

The open question is **closed by observation**.

`node_modules` was produced (`L1769`). The table has **no row for this symptom**, and that absence

## THE FINDING — `develop-gate` has no approval gate, and never has

### What IS enforced — the load-bearing claim from here on

From `gh api repos/JMSBPP/cfmm-vol-markets/branches/develop/protection`:

- `required_status_checks.contexts: ["gate"]` (app 15368), `strict: false`
- `required_pull_request_reviews.required_approving_review_count: 1`
- `enforce_admins: false` — so the owner can merge past the review, and did, for #59.

**Consequence that must outlive this phase: the `gate` job must NEVER be given a `name:`.**
`contexts: ["gate"]` matches the job's *check-run name*, which defaults to the job id. A rename
would silently un-protect `develop` — branch protection would wait on a context nothing ever
reports, or GitHub would treat it as never-required depending on configuration. Plan 05 asserted
`'name' not in gate` as a contract-preservation check; that assertion is now known to be the single
thing standing between this repo and an unprotected default branch. It is not stylistic.

### STANDING RULE — `environment:` is not evidence of an approval requirement

Only the environment's `protection_rules` are. This was stated wrongly throughout the phase and the
error propagated: the claim that `develop-gate`'s first job was a human approval step was repeated
to the maintainer and to a sibling project, and used to argue design decisions — including this
phase's own criterion 2, and the "PR-only; no double-approval from a push trigger" rationale written
into `develop-gate.yml`'s own comment. **It was read off the YAML's intent and never checked against
the API.** What caught it was polling `pending_deployments`, getting `[]` where a pause was
predicted, and going to the environments endpoint for the cause.

**Verification rule:** to claim an approval gate exists, read `protection_rules` on the environment
and `pending_deployments` on a real run. A workflow key is a *request* for a gate, not proof of one.
The same reasoning error would recur for `deployment_branch_policy`, and for required status checks
inferred from workflow YAML rather than read from `branches/<b>/protection`.
