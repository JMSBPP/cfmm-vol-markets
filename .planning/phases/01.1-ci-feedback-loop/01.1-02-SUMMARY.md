## Accomplishments

- **The pin exists as data, not prose.** `.github/foundry-version` is POSIX-sourceable under
  `set -u` (`sh -uc '. ./.github/foundry-version'` → ok) and exposes exactly three assignments —
  no fourth key crept in, no spaces around `=`, no command substitution. That is what makes
  "both workflows resolve the same pin" structural rather than aspirational: plans 03 and 05 will
  `.`-source this one file instead of each carrying its own version literal.
- **The pin asserts on the COMMIT, not the tag.** `FOUNDRY_COMMIT=b0a9dd9…` is the value the
  workflows will `grep -F` out of `forge --version`. A re-cut `1.5.1` tag would satisfy a
  tag-only check and change nothing visible; it cannot satisfy this one.
- **The reason is recorded next to the pin, with its measured numbers intact.**
  `notes/TOOLCHAIN_PINS.md` has all six sections and quotes the findings faithfully rather than
  paraphrasing them: the value-dependent coercion (`tokenId "0"` → `tuple(string,string,string)`
  vs `"18446744073709551616"` → `tuple(string,string,uint256)`), `b.length == 96` garbage on
  object returns, lazy `${...}` resolution in `[rpc_endpoints]`, the still-OPEN
  `try`/`catch`-vs-`extcodesize` question, and the founding failure mode at its measured
  **45.00 s per call with the test PASSED**.
- **The installer is pinned too**, and section 4 says why: an unpinned `foundryup-init.sh`
  fetched from a moving branch makes the toolchain pin conditional on a third party's default
  branch. The commit is the same one `foundry-rs/foundry-toolchain@v1` pins in its own
  `src/index.ts`.
- **Section 5 pre-commits the install location** to `$HOME/.foundry-pins/$FOUNDRY_VERSION`, with
  the argument for why NOT `$HOME/.foundry` (on a persistent runner that shared directory IS the
  box's default `forge`, so installing there would have CI rewrite the machine for every other
  job and human on it). Plan 03 implements a decision that is already written down and reviewable.
- **Nothing was pushed and nothing was built.** One commit ahead of
  `origin/feat/ci-feedback-loop`; `gh run list --branch feat/ci-feedback-loop` still returns
  empty; no `out/`, `cache/` or `node_modules/` in the worktree; all 13 submodules remain

## Decisions Made

- **One commit for two tasks, by plan instruction.** Task 1 explicitly forbids committing on its
  own. The pin and its reason are meant to arrive and to move together — the bump procedure in
  section 6 depends on that coupling being the norm, so splitting them would have taught the
  wrong shape on the very first commit.
- **`FOUNDRY_DIR` deliberately absent from the pin file.** Where the toolchain is installed is a
  per-workflow concern (and, per section 5, a deliberately non-default one); putting it in the
  pin would conflate the toolchain's identity with a runner-hygiene decision.
- **Nothing pushed.** The branch is one commit ahead locally. Plan 03's push is by construction
  the first push carrying `push-build.yml`, hence the first observable trigger; a push here would
  add a zero-information run-less push to the record plan 04 has to harvest.
- **The four findings were quoted, not summarised.** Section 2 carries `b.length == 96`, both
  `tokenId` coercion shapes, and `45.00 s` verbatim. A rationale that rounds its own evidence off
  cannot function as the thing a bump PR is forced to re-measure against.
