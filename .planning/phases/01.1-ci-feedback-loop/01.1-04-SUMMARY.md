## Accomplishments

- **The evidence file harvests TWO runs, because there are two and both matter.** The plan and the
  orchestrator both anticipated one. Run 1 is the *measurement*; run 2 is the *outcome*. Collapsing
  them into "it eventually went green" would discard the entire value of run 1.

- **The ROADMAP's open question is answered by observation.** `which -a forge`, identical in both
  runs:

      /home/jmsbpp/.foundry-pins/v1.5.1/bin/forge
      /home/jmsbpp/.foundry/bin/forge
      /home/jmsbpp/.foundry/bin/forge

  The box **did** already have its own forge — listed *twice* on `PATH` before CI touched anything —
  and the pinned binary won via the `$GITHUB_PATH` prepend without `$HOME/.foundry` ever being
  written to. `foundry-toolchain@v1` was rejected during planning by *reading its source*; run 1
  turns that from a good argument into a measured fact, and foundryup volunteered the confirmation:
  `There are multiple binaries with the name 'forge' present in your 'PATH'` /
  `You may need to run 'rm /home/jmsbpp/.foundry/bin/forge'`. That advice is right for a workstation
  and wrong for this runner; declining it is the design.

- **All four install-mechanism unknowns closed, each with a quoted line.** Runner egress to
  `raw.githubusercontent.com` works (`foundryup-init: binary verified ✓`); `flock` is present (the
  step reached its download branch under `set -euo pipefail`); `--install` is the right foundryup
  flag (`binaries not found or do not match expected hashes, downloading new binaries`); and
  `v1.5.1` really does build to the pin (`foundryup: use - forge 1.5.1-v1.5.1 (b0a9dd9ced …)`).
  Cold install cost: **19 s**.

- **A subtlety the plan could not have anticipated: the pin assertion is in the STAMP step, not the
  install step.** Run 2's install took **0 seconds and printed nothing** — the stamp file from run 1
  short-circuited the whole branch, so the `grep -qF "$FOUNDRY_COMMIT"` *inside* it never executed.
  The stamp step's own identical assertion did, and passed. The pin is therefore verified every run
  regardless of cache state, which is exactly what CI-06 needs — but it now rests on a single step,
  and that is written down.

- **The first green build in the project's history is on the record with its numbers.**
  `Ran 74 test suites in 11.21s (55.23s CPU time): 271 tests passed, 0 failed, 1 skipped (272 total
  tests)`. Against the last recorded local baseline of "252 passed, 0 failed", and with a **smaller**
  skip ledger (3 patterns, down from 4). More surface measured, fewer exclusions. The lone skip is
  `MevTaxVolumePathV4Test` waiting on an absent `loop-conformance.json` fixture — not a compile
  problem.

- **The regression floor held in CI for the first time.**
  `Suite result: ok. 10 passed; 0 failed; 0 skipped` for
  `test/protocol_integrations/VolOrderToPanopticTokenId.t.sol`. STATE.md has carried this as a
  standing reminder since the milestone opened; this is the first run that could actually check it.

- **A finding worth more than the fix it came from.** `--skip` matches on **filename**, so
