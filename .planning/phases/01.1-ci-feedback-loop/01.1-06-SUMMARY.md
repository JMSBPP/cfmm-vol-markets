## THE FINDING — `develop-gate` has no approval gate, and never has

Plan 05 predicted the gate run's `pending_deployments` would be non-empty — "that is
`environment: develop-gate` working, and is the deliberate difference from the push path". **It was
`[]` at every poll**, and the `approve` job ran unattended: run created `20:15:07Z`, `approve`
started `20:15:11Z` (+4 s), done `20:15:15Z`.

    $ gh api repos/JMSBPP/cfmm-vol-markets/environments/develop-gate
    "protection_rules": [],
    "deployment_branch_policy": null,
    "can_admins_bypass": true,
    "created_at": "2026-06-28T21:28:40Z",
    "updated_at": "2026-06-28T21:28:40Z"

`created_at == updated_at`: the environment has never been configured since the day it was created.
`environment: develop-gate` produces a deployment record and **no pause**.

**Pre-existing, and provably not this phase's doing.** Gate runs from 2026-08-26, before Phase 1.1
existed, show the same unattended `approve` — `33012911523` (+4 s) and `33008976085` (+3 s) — and
plan 05's `+84 / −0` proves nothing was removed. Total approvals for the whole change: **0**, not
the expected 1.

### What is actually enforced

- `required_status_checks.contexts: ["gate"]` (app 15368) on `develop`
- `required_pull_request_reviews.required_approving_review_count: 1`
- `enforce_admins: false` — so the owner can merge past the review, and did, for #59

**The consequence that must outlive this phase: the `gate` job must NEVER be given a `name:`.**
Branch protection binds to the check-run name, which defaults to the job id. A rename would silently
un-protect `develop`. Plan 05 asserted `'name' not in gate` as a contract-preservation check; that
assertion turns out to be the single thing standing between this repo and an unprotected default
branch. It is not stylistic, and the next person to tidy that workflow needs to know it.

### The reasoning error, recorded because it propagated

The claim that `develop-gate`'s first job was a human approval step was repeated to the maintainer
and to a sibling project, and used to argue design decisions — including this phase's own criterion
2, and the "PR-only; no double-approval from a push trigger" rationale written into
`develop-gate.yml`'s own comment. **It was read off the YAML's intent and never checked against the
API.** What caught it was polling `pending_deployments`, getting `[]` where a pause was predicted,
and going to the environments endpoint for the cause.

**Standing rule now in STATE.md:** `environment:` in a workflow is not evidence of an approval
requirement; only the environment's `protection_rules` are. The same error would recur for
`deployment_branch_policy`, and for required status checks inferred from workflow YAML rather than
read from `branches/<b>/protection`.

## Deviations from Plan

### Auto-fixed / handled

**1. [Rule 3 — Blocking] `rebase` refused; merged instead, to protect the dirty submodule pointers**

- **Found during:** Task 3
- **Issue:** `git rebase origin/develop` aborted with "cannot rebase: You have unstaged changes" —
  the working tree carries five pre-existing dirty entries the phase must not touch, two of which
  (`offchain`, `spec`) are **submodule gitlinks**. `rebase --autostash` would have stashed and
  restored all of them; stash round-trips on gitlinks do not reliably reproduce the original state
  because `git stash` does not recurse into submodule working directories.
- **Fix:** `git merge origin/develop` instead. Verified first that no path differing between
  `HEAD` and `origin/develop` overlapped any dirty path, so the merge could not touch them. Verified
  after that `git status --porcelain`, four `md5sum`s and both submodule `HEAD`s were byte-identical
  to the pre-merge snapshot.
- **Commit:** `e51237c`
