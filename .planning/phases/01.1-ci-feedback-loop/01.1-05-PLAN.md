### The gate is load-bearing in ways an edit can silently break

`develop-gate` is **the sole required check on `develop`**. Four of its properties are not
refactorable and are hard constraints on this plan:

1. **`on: pull_request` only.** Its own comment says why: "PR-only; merges go through PRs (no
   double-approval from a push trigger)". Adding any trigger here would create exactly the second
   approval, or the push path into the merge gate, that this whole phase was designed to avoid.
2. **The `approve` job is the ONLY `environment:` reference** — deliberately, so there is exactly
   one approval and it happens before untrusted code runs.
3. **The `gate` job's result loop encodes a real incident.** A REJECTED environment review once
   produced `approve=failure` → every heavy job `skipped` → the loop accepted `skipped` → "all
   gate jobs green", exit 0, with zero tests having run. The fix depends on `approve` being the
   single dependency every heavy job declares, which is why the comment says adding an `if:` to
   any job would reopen it. Do not add one.
4. **The `gate` job must not gain a `name:`** — that changes the required-check context string and
   silently detaches the branch protection rule.

Also fixed by phase constraint: **the `--skip` ledger line and `--fuzz-seed 4880` do not change**,
and `scripts/check-ci-skip-ledger.sh` will fail the push build if they do.

### Why the plank job is not touched

`develop-gate`'s `plank` job runs `git submodule update`, `make plank-toolchain` and
`make compile-plank`. It never invokes `forge`. Installing a Foundry toolchain there would be dead
weight on the critical path of every PR. CI-06's "each run's log shows the resolved
`forge --version`" is discharged by the job that actually uses forge.

### Why the ledger-parity guard is not added to the gate either

It would be harmless, and it is still not added. The phase constraint is that the gate's edit stay
minimal and provably additive. Drift is introduced by an edit, an edit arrives by a push, and every
push already runs the guard. A second copy buys nothing and widens the diff on the one workflow
that must stay reviewable at a glance.

### The mechanism, as proven by plan 04

Identical to `push-build.yml`'s two steps: source `.github/foundry-version`, install the pinned
release via the pinned `foundryup` installer into `$HOME/.foundry-pins/$FOUNDRY_VERSION` under an
`flock`, prepend that `bin` to `$GITHUB_PATH`, then `forge --version | tee`, write it to
`$GITHUB_STEP_SUMMARY`, and `grep -qF "$FOUNDRY_COMMIT"` or fail. On the persistent runner the pin
directory and its stamp file already exist from plan 03's run, so this is a fast no-op install —
that reuse is the point of keying the directory by pin.

**If plan 04's evidence recorded an adjustment to the mechanism** (e.g. `flock` absent, or the
installer commit bumped), apply the SAME adjusted body here and back-port it to
`push-build.yml` in the same commit. The two workflows must not diverge; that is the entire
reason the pin lives in one file.

**Insert two steps into the `forge` job, immediately after its `actions/checkout@v4` step (which

Insert exactly this, at the existing step indentation (six spaces before `- name:`):

      # The toolchain is resolved from the tracked pin, not from whatever `forge` this
      # PERSISTENT runner happens to have. Requirement CI-05; the reason, and the four measured
      # findings that depend on b0a9dd9, are in notes/TOOLCHAIN_PINS.md. Placed BEFORE the
      # submodule/plank/npm work on purpose: a wrong toolchain fails here in seconds rather than
      # after twenty minutes of setup. Body is byte-identical to push-build.yml's -- one pin,
      # one mechanism, two workflows.
      - name: Install the pinned Foundry toolchain
        run: |
          set -euo pipefail
          . ./.github/foundry-version
          : "${FOUNDRY_VERSION:?}" "${FOUNDRY_COMMIT:?}" "${FOUNDRYUP_INSTALLER_COMMIT:?}"

          # NOT $HOME/.foundry: on this persistent runner that is the box's shared foundry dir
          # (and where foundry-rs/foundry-toolchain@v1 would install -- src/index.ts:
          # FOUNDRY_DIR = path.join(os.homedir(), ".foundry")). Installing there would have CI
          # rewrite the machine's default forge. A per-pin directory cannot collide, and
          # $GITHUB_PATH is PREPENDED, so the pinned binary wins for this job only.
          PINS="$HOME/.foundry-pins"
          export FOUNDRY_DIR="$PINS/$FOUNDRY_VERSION"
          STAMP="$FOUNDRY_DIR/.installed-$FOUNDRY_COMMIT"
          mkdir -p "$PINS"

          # The push build can be installing the same pin concurrently on this runner.
          # Serialize; the stamp -- written only after the commit assertion below -- makes the
          # second entrant a no-op and stops a half-finished install from looking good.
          exec 9>"$PINS/.lock"
          flock 9

          if [ ! -f "$STAMP" ]; then
            mkdir -p "$FOUNDRY_DIR"
            curl -fsSL --retry 3 \
              "https://raw.githubusercontent.com/foundry-rs/foundryup/${FOUNDRYUP_INSTALLER_COMMIT}/foundryup-init.sh" \
              -o "$RUNNER_TEMP/foundryup-init.sh"
            # Non-zero with "could not detect shell" is the normal CI case (no rc file to edit);
            # foundry-toolchain@v1 swallows exactly this string. Anything else is real.
            set +e
            out="$(bash "$RUNNER_TEMP/foundryup-init.sh" 2>&1)"; rc=$?
            set -e
            printf '%s\n' "$out"
            if [ "$rc" -ne 0 ] && ! printf '%s' "$out" | grep -q 'could not detect shell'; then
              echo "::error::foundryup-init.sh failed (exit $rc)"; exit 1
            fi
            "$FOUNDRY_DIR/bin/foundryup" --install "${FOUNDRY_VERSION#v}"
            "$FOUNDRY_DIR/bin/forge" --version | grep -qF "$FOUNDRY_COMMIT" || {
              echo "::error::foundryup installed a forge whose commit is not $FOUNDRY_COMMIT"
              exit 1
            }
            touch "$STAMP"
          fi
          echo "$FOUNDRY_DIR/bin" >> "$GITHUB_PATH"

      # CI-06: every gate run carries the resolved toolchain as evidence, in the log and in the
      # run summary, and a mismatch is RED. `which -a forge` records the collision with the
      # runner's pre-existing forge so "which binary ran" is never a guess. The assertion greps
      # the whole output for the commit rather than parsing a named line, so a change to forge's
      # --version format is not a false red.
      - name: Stamp the resolved forge version
        run: |
          set -euo pipefail
          . ./.github/foundry-version
          which -a forge || true
          forge --version | tee "$RUNNER_TEMP/forge-version.txt"
          {
            echo "### Foundry toolchain (pinned)"
            echo ""
            echo '```'
            cat "$RUNNER_TEMP/forge-version.txt"
            echo '```'
            echo ""
            echo "pin: \`$FOUNDRY_VERSION\` / \`$FOUNDRY_COMMIT\` (.github/foundry-version)"
          } >> "$GITHUB_STEP_SUMMARY"
          grep -qF "$FOUNDRY_COMMIT" "$RUNNER_TEMP/forge-version.txt" || {
            echo "::error::resolved forge does not match the pin in .github/foundry-version"
            exit 1
          }
