   also tells you which assumption broke):

| Symptom in the log | Meaning | Remedy (belongs in a follow-up plan, not this one) |
|---|---|---|
| No run at all in `gh run list` | Actions disabled on the fork, or the workflow file was rejected | Check `gh api repos/$REPO/actions/permissions`; check the Actions tab for a syntax error banner |
| Job queued forever, never starts | No online runner with BOTH labels `self-hosted` and `cfmm-build` | `gh api repos/$REPO/actions/runners` — compare labels against `develop-gate`'s working `forge` job |
| `flock: command not found` | `util-linux` absent on the runner | Replace the lock with `mkdir`-based mutual exclusion; the pin-keyed dir and stamp are unaffected |
| `curl: (6)`/`(7)`/`(35)` on raw.githubusercontent.com | No outbound access from the runner | The whole download-based approach is unavailable; fall back to asserting a pre-provisioned pinned binary and provisioning it on the box once, out of band |
| `foundryup: unknown option --install` | The installer pin predates the `--install` flag | Bump `FOUNDRYUP_INSTALLER_COMMIT`; `--version` was the older spelling |
| `foundryup` installs a different commit | The `v1.5.1` tag does not build to `b0a9dd9…` | STOP. This invalidates the pin's premise; escalate rather than relaxing the assertion |
| stamp step red: `resolved forge does not match the pin` | A stale `.foundry-pins` dir, or PATH not prepended | Read the `which -a forge` lines in the same step; they say which binary answered |
| `forge build` red on `@cryptoalgebra` | `npm ci` did not produce `node_modules` | The `Node dependencies` step's own conclusion says whether it ran |
| Job killed at 30 min | `cargo build --release` of plankc dominates on a cold runner | Raise `timeout-minutes`; do NOT drop `make plank-toolchain` — it is why a pin bump does not fail every plank build |
