tested offline against frozen fixtures.

This plan exists because the premium read route (`SFPM.getAccountPremium` via archive `eth_call`)
needs three things Phase 9 never built: ABI encoding of a struct argument, decoding of packed
`uint128` return words, and a JSON-RPC call other than `eth_getLogs`. It also fixes a latent hazard:
`Panel.Variance` carries the only retry/backoff implementation in the repo, and copying it would
create the exact kind of divergence that produced the 09-05 epoch-offset trap. `Chain.Rpc` is
**lifted out** of `Panel.Variance`, which then imports it.

being right. Each is cheap to test in isolation and catastrophic to get wrong at scale.

Implementation requirements — each of these is load-bearing, do not "simplify":

- `decodeWordAt :: Bool -> Int -> ByteString -> Integer` generalises `Panel.Variance.wordAt`
  verbatim: `Bool` = signed, `Int` = 32-byte word index into the returndata. When `signed` is
  `True`, apply two's-complement sign extension over the FULL 32-byte word (that is how Solidity
  ABI-encodes `int24`: sign-extended to 256 bits, so a negative tick appears as
  `0xffff...fffcf...`). `Panel.Variance.wordAt` must be deleted and replaced by a re-export of
  `decodeWordAt` so there is exactly one implementation; `decodeTick` and `decodeSqrtPriceX96`
  keep their current signatures and behaviour.

- `encodeInt24 :: Int -> ByteString` — 32-byte big-endian two's-complement. `encodeAddress` —
  32-byte left-padded 20-byte address (accepts a `0x`-prefixed `Text`).
  `encodeBytesDynamic :: ByteString -> (ByteString, ByteString)` returns the (head-slot offset
  placeholder, tail) pair for a dynamic `bytes` argument: the tail is
  `encodeUint256 (length bs) <> bs` right-padded to a 32-byte multiple. This is needed because
  `getAccountPremium`'s first argument is `bytes poolKey`, a DYNAMIC type — its head slot holds a
  byte offset, not the data. Getting this wrong yields a silent revert or garbage.

- `decodeUint128Pair :: Integer -> (Integer, Integer)` returns
  `(word `div` 2^128, word `mod` 2^128)` = `(leftSlot, rightSlot)`. Per RESEARCH
  ("LeftRight packing: right slot = currency0, left slot = currency1"), **right slot is currency0
  (ETH)** — the reconciliation target. Document this in a comment; a swap here silently reconciles
  against USDC and fails the gate for the wrong reason.

- `diffMod :: Int -> Integer -> Integer -> Integer`,
  `diffMod n a b = (a - b) `mod` (2 ^ n)`. Haskell's `mod` on `Integer` already returns a
  non-negative result for a positive modulus — that is exactly the Solidity `unchecked` semantics.
  Do NOT use `rem`. Do NOT guard with `if a >= b`. Add a comment citing RESEARCH Pitfall 3: a naive
  `a - b` produces ~-1.15e77 instead of ~1e19 whenever the accumulator has wrapped.

- `feeGrowthInside :: Int -> Int -> Int -> Integer -> Integer -> Integer -> Integer`
  with argument order `tickCurrent tickLower tickUpper global lowerOutside upperOutside`,
  implementing `Pool.sol` L488-511 exactly:
  ```
  tickCurrent <  tickLower  ->  diffMod 256 lowerOutside upperOutside
  tickCurrent >= tickUpper  ->  diffMod 256 upperOutside lowerOutside
  otherwise                 ->  (global - lowerOutside - upperOutside) `mod` 2^256
  ```
  Note the boundary: `>=` on the upper side, `<` on the lower side. Add a comment recording the
  RESEARCH "tick off-by-one trap": always use the STORED `slot0.tick` (which is what the `Swap`
  event reports and what `Panel.Variance` caches), never a re-derivation from `sqrtPriceX96`, which
  can be one lower after a `zeroForOne` crossing.

- `keccak256Hex :: ByteString -> Text` using `Crypto.Hash.Keccak_256` from **`crypton`**
  (add `crypton` and `memory` to the `library` dependency list in `package.yaml`). Ethereum uses
  legacy Keccak-256, NOT SHA3-256 — they differ in padding and would silently produce wrong
  selectors. `selector :: Text -> ByteString` = first 4 bytes of `keccak256Hex` of the UTF-8
  signature.
