```haskell
data EventId = EventId { ev_tx_hash :: !String, ev_log_index :: !Integer } deriving (Eq, Ord, Show)

data LedgerRow = LedgerRow
  { lr_event      :: !EventId
  , lr_block      :: !Integer
  , lr_model      :: !String
  , lr_key_scheme :: !KeyScheme
  , lr_key        :: !(Maybe BS.ByteString)
  , lr_outcome    :: !Outcome
  , lr_reason     :: !String
  , lr_gams_ver   :: !String
  , lr_conopt_ver :: !String
  } deriving (Eq, Show)

data Ledger = Ledger
  { ledger_label        :: String
  , ledger_commit_block :: Integer -> [LedgerRow] -> IO ()
  , ledger_seen         :: EventId -> IO Bool
  , ledger_rows_for     :: EventId -> IO [LedgerRow]
  , ledger_watermark    :: IO (Maybe Integer)
  }

new_memory_ledger   :: IO Ledger
new_postgres_ledger :: Connection -> Ledger
```

`ledger_commit_block b rows` is **one transaction and one call** — the block's rows and that block's
watermark advance are indivisible by construction, so there is no arity at which a caller can commit
rows and forget the watermark, and no ordering bug to write. Postgres implementation:
`withTransaction con $ do { mapM_ (insert with "on conflict on constraint loop_event_identity do nothing") rows;
insert into loop_watermark (only_row, block) values (true, ?) on conflict (only_row) do update set block = excluded.block, updated_at = now() }`.
`key` goes through `Binary` exactly as `Store.Postgres.put_run` does — read that function, do not
invent a second convention. The memory implementation holds one `IORef (Map (String,Integer) LedgerRow)`
and one `IORef (Maybe Integer)`, applies the same first-writer-wins on the event identity, and
commits both refs under one `atomicModifyIORef'`-style step so a partially-applied commit is not
representable there either.

`ledger_seen` is what stops re-work on a REPLAYED EVENT. It is a different mechanism from the content
key, which stops re-solving an identical SHOCK, and both must exist: the first preserves chronology,
the second preserves work. Say so in the haddock — LOOP-02's criterion asserts both directions and
collapsing them destroys the chronology the run log exists to provide.

No `aeson`, no `Double`, no hexadecimal literal, no credential-shaped string.
